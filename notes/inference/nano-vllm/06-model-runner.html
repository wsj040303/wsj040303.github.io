enforce_eager 控制什么，为什么调试时常用 eager

需要区分两个时刻：初始化时要不要捕获图，真正运行时要不要重放图。 第一段位于 __init__()：enforce_eager=True 时跳过图捕获。第二段位于 run_model()：prefill、强制 eager 或实际 batch 超过 512 时，直接调用模型。其余情况才进入选择 Graph 档位的分支。图中把这两次判断分开画出。

eager 路径每轮都会执行 Python 前向调用，便于在模型中加打印、断点或查看报错位置。Graph 路径会重放预先捕获的 GPU 工作；图内的 Python 代码不会在每次重放时重新执行。因此调试模型计算过程时，可以先用 enforce_eager=True。

为什么非 rank 0 进程停在 loop()，rank 0 却继续运行

rank 0 所在进程要继续运行请求调度，其他 rank 则等待它发来同一轮模型计算的指令。 调度决策由该进程中的 Scheduler 做出；ModelRunner 的职责是执行已经选好的请求。rank 0 创建 1 MiB 的 CPU 共享内存，其他 rank 在初始化屏障之后打开它。world_size=1 时不创建这条共享内存消息通路。

例如引擎调用 model_runner.call("run", seqs, is_prefill)：rank 0 先通过 write_shm() 写入方法名和参数，再执行自己的 run()。每个 worker 的 Event 被设置后，从共享内存读取同一条命令，进入自己的 call()，并在各自 GPU 上参与模型计算。

read_shm() 中的 event.wait() 使 worker 在没有新命令时等待；消息前 4 字节是长度，后面是 pickle 序列化的 [method_name, *args]。getattr(self, method_name) 根据名字找到 run 或 exit；*args 把收到的参数列表展开成位置参数。event.clear() 在方法执行前就发生，因此它表示“这条消息已读”，不能当成“模型计算已完成”的通知。

loop() 没有保存 self.call(...) 的返回值。源码中只有 rank 0 调用采样器并返回 token ID 列表，其他 rank 的 run() 返回 None；模型的张量并行通信通过 NCCL 完成。收到 exit 时，worker 先运行清理方法，再退出循环。LLMEngine.step() 与调用入口、ModelRunner.run()

已扣掉 used，为什么还要预留 peak - current

问题在于：分配 KV Cache 时看到的是预热结束后的占用，下一次前向计算还会再次需要临时张量。 warmup_model() 在运行合成 batch 前重置峰值统计；计算结束，一部分中间结果释放，当前分配量回落。peak 是这一统计期内的分配峰值，包含常驻张量和当时的临时张量；current 是现在还持有的分配量。两者差值才是源码用来预留的临时增量。PyTorch allocated_bytes 统计定义

used 与 current 来自不同统计范围。used = total - free 是 CUDA 驱动看到的当前设备占用；current 来自本进程的 PyTorch 分配器，已经包含在当前占用中。若把下一轮的 PyTorch 占用估计为 peak，总运行占用可以写成 used - current + peak。将这个估计值从目标预算扣除，就得到源码中的：

图中是假设算例：总显存 24 GiB，利用率 0.9，所以目标预算为 21.6 GiB；当前 used=current=18 GiB，预热 peak=20 GiB。若只减当前占用，会给 KV Cache 留出 3.6 GiB，之后再出现 2 GiB 临时增量，预计占用变成 23.6 GiB，超过目标预算。扣除增量后，KV 预算约为 1.6 GiB；若每块占 1 MiB，向下取整为 1638 块。

这里估计的是预热负载下的临时增量。实际输入、其他进程占用以及后续 CUDA Graph 捕获都会影响显存需求；“不超过目标预算”也不同于“绝不会发生显存不足”。尤其本文件先分配 KV Cache，再捕获图，不能把 peak-current 当成已经测过所有 Graph 档位的额外占用。

CUDA Graph 是什么、如何加速，以及固定档位的代价

1. CUDA Graph 是什么

CUDA Graph 是一份可以重复执行的 GPU 工作图。 图中的节点代表 GPU 操作，连线表示操作之间的依赖关系。在这里，torch.cuda.graph(...) 把模型前向涉及的 GPU 操作、执行依赖及其使用的内存地址记录下来，这个过程叫作捕获。之后调用 graph.replay()，就可以按记录重新运行这批工作。

每轮输入仍然可以不同：先把新 token 等数据写进图所使用的输入缓冲区，再重放。模型会根据新数据重新计算，所以捕获的是执行过程，不是提前算好的答案。本文件捕获 self.model(...) 和输出写入；后面的 compute_logits() 与 token 采样位于这次捕获范围之外。PyTorch CUDA Graph 说明

2. 它为什么能加速

主要节省的是 CPU 反复向 GPU 提交工作的开销。 普通 eager 执行时，CPU 每轮都要经过框架调度，把模型中的 GPU 操作陆续提交出去。如果每个操作本身很短，GPU 就可能花时间等下一项工作到来。Graph 把已捕获的操作作为一组工作提交，减少重复的调度、参数准备和启动开销。

decode 每轮为每个请求处理一个 token，小 batch 时更容易受到这类提交开销影响，因此本实现用 Graph 优化 decode。重放仍然要执行模型计算，也仍有输入复制、图外输出头和采样等工作；当主要时间已经花在 GPU 计算上时，省去提交开销带来的收益就会相对小一些。

3. 固定大小为什么会占显存、造成补齐浪费

这份实现的每张图按提前确定的 batch 大小捕获，重放时沿用相同的张量形状和地址。 因此，输入、输出及捕获期间使用的中间缓冲区需要在图被持续复用期间保持有效，会占用显存。上面的代码先按 max_bs 分配输入输出缓冲；后续不同档位还共用 graph_pool 来减少重复分配，但共享池并不能消除这部分常驻占用。PyTorch 图内存管理

在同一档位区间里，刚超过前一个档位时，补齐浪费最大；越接近当前档位上限，补齐越少。 对 16 到 32 这段而言，17 个请求就是最明显的边界情况。源码把补齐行的 KV 写入槽位设为 -1、上下文长度设为 0，最终只取 outputs[:bs]，但模型仍有按较大形状执行的额外工作。表格描述的是补齐行的比例，不等于延迟增加比例。

这就形成了档位设计的取舍：档位密一些，可以减少补齐计算，却需要捕获和维护更多图；档位稀一些，捕获数量更少，但刚跨过档位边界时会多算很多行。Graph 带来的提交加速，需要与常驻显存和补齐开销一起考虑。
