先建立一张地图

CUDA 是 NVIDIA 的并行计算平台与编程模型。写 CUDA C++ 时，CPU 上的 Host 代码负责准备数据、分配内存并启动任务；GPU 上的 Device 执行称为 Kernel 的函数。一次 Kernel 启动会创建许多线程，让它们处理不同的数据下标。

本篇按三个问题展开：线程怎样组织？这些线程落到哪些硬件上？数据放在哪里？最后用向量加法把三者连起来。图均为本站依据 NVIDIA 文档绘制的概念图，表示编程模型与常见硬件对应关系，不代表某一型号 GPU 的精确布线。

先记住这句话

Kernel 写的是“一个线程要做什么”；启动配置指定“总共让多少线程执行”。线程通过自己的索引找到负责的数据。

执行层次：Grid → Block → Warp → Thread

一次 Kernel 启动对应一个 Grid（网格）；Grid 由多个 Block（线程块）组成；Block 包含多个 Thread（线程）。Block 和 Grid 都可以是一、二或三维，便于把数组、图像或体数据映射到线程。NVIDIA GPU 执行时，还会把一个 Block 中的线程组织成每组 32 个线程的 Warp。Warp 是硬件调度的重要单位，但普通 CUDA Kernel 仍以每个线程的视角写代码。

层次是什么初学者最该记住的事
Grid一次 Kernel 启动的全部 BlockGrid 的大小决定有多少 Block；它不是一块物理芯片。
Block一组协作的线程同一 Block 的线程在同一个 SM 上执行，可使用共享内存和块内同步。
Warp一个 Block 内的一组 32 个线程同一 Warp 的线程以 SIMT 方式执行；分支路径不同可能降低效率。
Thread运行 Kernel 代码的一个逻辑实例用索引决定自己处理哪份数据，通常持有私有变量。

从局部索引算出全局索引

最常见的一维场景里，threadIdx.x 是线程在 Block 内的编号，blockIdx.x 是 Block 在 Grid 内的编号，blockDim.x 是每个 Block 的线程数。所以：

全局下标 i = blockIdx.x × blockDim.x + threadIdx.x

例如用 256 个线程组成一个 Block，blockIdx.x = 2、threadIdx.x = 7 的线程处理下标 2 × 256 + 7 = 519。若数据长度是 1000，需要 (1000 + 255) / 256 = 4 个 Block，总共启动 1024 个线程；最后 24 个线程必须用 if (i < n) 跳过越界元素。

Block 之间的关系

普通 Kernel 不保证不同 Block 的执行顺序，也不能直接用 __syncthreads() 做跨 Block 屏障。一个 Block 的线程在同一 SM 上；多个 Block 是否能同时驻留该 SM，取决于寄存器、共享内存、线程数等资源。较新的 GPU 还支持可选的 Thread Block Cluster；先掌握普通 Grid / Block 即可。

从编程模型走到硬件：GPU 与 SM

GPU 有多个 SM（Streaming Multiprocessor，流式多处理器）。可以把 SM 理解为执行线程块的主要硬件场所：一个 Block 的全部线程落在同一 SM；Grid 的不同 Block 由 GPU 分配到可用 SM，数量多时分批执行。每个 SM 具有执行单元、寄存器文件、共享内存以及缓存等资源；设备级的 L2 缓存和全局内存服务于多个 SM。

Grid、Block 和 SM 不属于同一套层次：Grid / Block / Thread 是程序指定的逻辑层次；SM、寄存器文件、缓存、显存是硬件资源。Warp 位于两者的交界：程序中的线程会被组织成 Warp，由 SM 调度执行。不同架构的 SM 内部实现与资源上限会变化，因此选择 Block 大小时应看目标 GPU 的规格和测量结果。

内存层次：谁能看见，存多久，在哪里

理解 CUDA 内存时，先看作用范围，再看速度。线程私有的值通常放在寄存器；同一 Block 的线程可通过共享内存交换数据；全局内存对设备上的线程可见，并在 Kernel 结束后继续存在，直到释放。缓存由硬件管理，不能简单地当成程序可显式分配的共享内存。

空间谁可以使用位置 / 生命周期常见用途
寄存器 Registers单个线程SM 上；随线程执行循环变量、临时计算结果。
共享内存 Shared Memory同一 Block 的线程SM 上；随 Block 生命周期线程协作、数据复用、分块计算。
局部内存 Local Memory单个线程逻辑上私有，通常以设备内存为后备放不进寄存器的私有数据、寄存器溢出等。
全局内存 Global Memory设备上的线程GPU 设备内存；分配后直到释放输入、输出和大数组。
常量内存 Constant Memory设备线程只读设备内存；有专用缓存Kernel 中不变的小型参数。

L1 / L2 是缓存层：L1 与 SM 相关，L2 为设备级共享缓存；它们会影响全局内存访问成本，但与上述由代码声明或分配的内存空间不是同一套分类。local 的“局部”指仅本线程可访问，不等于“物理上离计算单元近”。

数据怎么移动

下面的向量加法使用显式管理：Host 用 cudaMalloc 在 GPU 分配全局内存，用 cudaMemcpy 把输入从 Host 复制到 Device；Kernel 从全局内存读入操作数、计算并写回；最后将输出复制回 Host。cudaMallocManaged 提供统一内存的另一种写法，但“统一地址”不意味着数据搬移成本消失。

当相邻线程访问相邻地址时，硬件通常能把它们的全局内存访问更有效地合并；需要反复使用的数据可考虑搬到共享内存。共享内存的读写也需要正确的线程同步，不能把它当成自动同步的缓存。

性能分析：先测量，再解释

向量加法每个元素读取两个 float、写入一个 float，理论上至少涉及 12 字节的设备数据流量（不计缓存与额外事务），但只做一次加法。对于足够大的数组，它常是带宽受限问题；对于这里的 1000 个元素，启动和调度开销也很明显。不能仅凭这一小例子推断设备带宽。

拿到时间后看什么

  1. 正确性：先验证输出和 CUDA 错误；错误结果没有性能意义。
  2. 访存：相邻线程是否访问相邻地址？是否出现无谓的重复读取？可在 Nsight Compute 的 Memory Workload Analysis 查看相关指标。
  3. 并行度：Block 数是否足以分布到多个 SM？寄存器、共享内存或 Block 大小是否限制可驻留 Warp？可查看 Occupancy 与 Launch Stats。
  4. 瓶颈：对大规模向量加法，用理论流量 12 × n 字节除以测得时间，估算有效带宽，再与同设备的测量结果比较；不要把这个估算直接当成显存硬件峰值。

可以从 ncu ./vector_add 开始查看 Kernel 报告。Occupancy 高不保证一定快；最终以同条件下的正确结果与实测时间为准。

把层次串起来

Host 启动一个 Kernel → 产生一个 Grid → Grid 划为多个 Block → 每个 Block 的线程在同一 SM 上执行并组成 Warp。数据从 Host 进入设备全局内存；线程用寄存器存私有临时值，同一 Block 可用共享内存协作，所有 Block 可以访问全局内存。写 Kernel 时先算对全局索引和边界，再测量是否需要优化访存与并行度。
