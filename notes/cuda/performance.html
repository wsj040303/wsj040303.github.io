测试目标与计时范围

CUDA 性能测试先固定一个工作负载，再比较同一工作负载下的实现。工作负载至少包括输入形状、数据类型、内存布局、数值范围和正确性标准；测试记录还应包含 GPU 型号、驱动、CUDA Toolkit、编译选项、线程块配置、热身次数与统计方法。不同输入规模可能使同一算子分别受启动开销、缓存或显存访问限制，因此单个尺寸的结果只适用于对应场景。

端到端耗时从调用方开始执行到结果可用为止，包含必要的数据传输、分配、启动与同步；Kernel 耗时只覆盖 GPU 上指定 Kernel 的执行区间。两者回答不同的问题：前者判断程序对用户是否变快，后者解释设备端代码的变化。Host 发起 Kernel 启动后可能立即继续执行，因此用 CPU 时钟围住启动语句时，须在结束计时前同步；CUDA Event 则适合测量同一 Stream 中排入的 GPU 工作。参见 CUDA C++ Best Practices Guide · Timing。

当算子已嵌入应用，先记录端到端时间，再分解 Kernel、复制和 CPU 侧间隙。单独的 Kernel 变快，不保证包含分配、传输与调度的路径也按相同比例变快。独立 microbenchmark 则要明确输入是否已驻留设备，以及每次重复是否复用同一块数据；缓存状态会改变测得的内存性能。

正确性与基线测量

在计时前，先用参考结果校验所有输出，包括非整除线程块的尾部输入和生产环境会遇到的边界形状。每次启动后检查 cudaGetLastError()，并在需要结果时同步以捕获执行期错误。性能版本与基线版本应采用相同的输入、输出、精度要求和计时范围；浮点归约若改变求和顺序，需要按业务误差要求比较。

CUDA Event 记录到 Stream 中；等待结束 Event 后，cudaEventElapsedTime 返回两次记录之间的毫秒。以下片段用 Event 围住一次 Kernel 启动，并将结果换算成微秒；完整的分配、热身、重复测量和校验见可下载的 CUDA C++ 示例。Event 与被测 Kernel 必须排入同一 Stream。参见 CUDA Runtime API · Event Management。

先完成数次不计入统计的热身，再采集多次结果，报告中位数和多次独立运行的范围。热身使初始化和编译加载等一次性工作退出被测区间；逐次同步便于得到每次 Kernel 的时间。运行时应尽量避免其他 GPU 任务争用资源，并保持两个版本的测量顺序与条件一致。对微秒级 Kernel，Event、启动和调度开销可能与执行时间同量级，此时还需要测量完整调用路径。

带宽受限候选算子可计算算法有效带宽：(按算法计的读字节数 + 写字节数) / Kernel 秒数，单位为 GB/s 时除以 109。这个值来自算法访问量与时间，并非硬件计数器测得的 DRAM 流量；数据命中缓存时，两者尤其不能直接等同。理论带宽、有效带宽及单位口径见 CUDA C++ Best Practices Guide · Bandwidth。

程序级时间线

Nsight Systems（nsys）记录 CUDA API、Kernel 和内存复制的时间线。它适合先定位程序花时间的位置：若 CPU 侧频繁分配或同步、Kernel 之间有较长空隙、传输与计算没有预期的重叠，应先检查调用路径。汇总表显示总量，时间线显示先后与重叠关系；只把不同类别的汇总时间相加，不能还原端到端墙钟时间。命令与统计报告见 Nsight Systems User Guide · Stats。

在本文示例的一次采集中，cuda_gpu_kern_sum 分别汇总了两个 Kernel 的 26 次启动；cuda_api_sum 同时显示了内存分配、复制与 Event 同步。这些值用于判断工作发生的位置。最终性能比较仍采用未启用分析器时的基线，因为采集本身会改变执行环境。

Kernel 指标分析

Nsight Compute（ncu）分析被选中的 Kernel。先用 SpeedOfLight 查看计算、DRAM、L1/TEX 和 L2 等部件的吞吐，再按怀疑点采集 MemoryWorkloadAnalysis、LaunchStats 或 WarpStateStats。指标需要结合输入规模和访存路径解释：高 DRAM 吞吐可说明显存通路接近当前采集条件下的峰值；低 DRAM 吞吐也可能是数据命中 L2、访存不合并、并行度不足或其他资源限制。Occupancy 是活跃 Warp 比例，增加 Occupancy 不必然提高性能。参见 Nsight Compute Profiling Guide 和 CUDA C++ Best Practices Guide · Occupancy。

示例程序先做一次正确性启动，再热身 5 次；-s 6 跳过这些同名启动，-c 1 只采下一次。采集复杂指标时，ncu 可能重放 Kernel，并按自身的时钟、缓存和串行化设置运行；采集范围和过滤参数见 Nsight Compute CLI 手册。因此，ncu 报告中的 Duration 和分析器内打印的 Event 时间用于诊断，不作为未插桩版本的加速比。参见 Nsight Compute Profiling Guide · Workload Durations。

访存映射实测

实验保持计算和启动配置相同，只改变线程与元素的对应关系。连续版本的一个 Warp 处理相邻下标；跨步版本的相邻线程访问相隔 gridDim.x 个 float 的地址。两者都完整覆盖输入，并已逐元素校验输出。按照 CUDA 的全局内存合并访问规则，连续地址通常需要更少的内存事务；跨步版本用于隔离这种映射的代价。参见 CUDA C++ Best Practices Guide · Coalesced Access。

本机为 NVIDIA GeForce RTX 5070（计算能力 12.0，驱动 595.91.07），使用 CUDA Toolkit 13.4 的 nvcc -O3 -std=c++17 -arch=sm_120 编译；分析工具分别为 Nsight Systems 2026.3.2 和 Nsight Compute 2026.3.1。输入为 16,777,216 个 float，每个数组 64 MiB，两个输入和一个输出合计 192 MiB；Block 为 256 线程。每个版本先热身 5 次，再以 Event 计时 20 次并取中位数。下表给出三次独立、未启用分析器的运行范围；运行期间未手动锁定 GPU 时钟。

线程映射Kernel 时间中位数范围算法有效带宽范围
连续访问335.4–335.6 µs599.9–600.2 GB/s
跨步访问894.0–896.1 µs224.7–225.2 GB/s

每个元素读取两个 4 字节输入并写入一个 4 字节输出，因此算法访问量为 16,777,216 × 12 = 201,326,592 字节。以 335.6 µs 为例，有效带宽约为 201,326,592 / 335.6 µs = 599.9 GB/s。连续版本在这组条件下约快 2.66 倍。单次 ncu 采集中，两个版本的全局加载请求数都为 1,048,576，但连续版产生 4,194,304 个 L1 sector（每请求 4 个），跨步版产生 33,554,432 个（每请求 32 个）。这直接支持了访问映射改变内存请求效率的判断。两次采集中的连续版 DRAM Throughput 为 91.70%，跨步版 L2 Cache Throughput 为 87.99%；这些百分比属于分析器条件下的诊断指标，不能替代上表的时间比较，也不能由 sector 比例直接推算耗时比例。

调优迭代

调优按“正确性 → 未插桩基线 → 程序时间线 → 单个 Kernel 指标 → 一项改动 → 同口径复测”循环进行。先用时间线确定开销位置，再从与该位置相关的指标提出具体假设。下表中的动作是待验证的候选方案；每次只改变可解释的一项，并同时记录性能与正确性结果。

观察位置进一步核查候选改动
程序时间线有大量复制、分配或同步核对必要的数据传输次数、API 调用与 Kernel 间隙复用设备内存、减少往返传输或不必要的同步，并复测端到端时间
Kernel 内存通路繁忙核对相邻线程的地址、全局内存请求及 L1/L2/DRAM 吞吐调整线程映射或数据布局；有复用时再评估分块与共享内存
Kernel 发射效率低或等待较多结合 LaunchStats 的寄存器与共享内存用量、WarpStateStats 的等待原因按实际限制调整 Block、每线程工作量或同步方式
源码改动未产生预期收益核对编译后的指令、寄存器数与未插桩时间确认编译器是否生成预期访存或计算指令，再调整实现

WarpStateStats 中的等待分类只有在调度器无法持续发射指令时才应作为主要优化线索；等待计数本身不等于性能损失。若需要核对编译器实际生成的代码，可用 nvcc -Xptxas=-v 查看寄存器与共享内存用量，用 cuobjdump --dump-sass ./cuda_perf_bench 查看设备指令。SASS 是编译产物证据，最终收益仍由正确性与同口径计时决定。参见 Nsight Compute Profiling Guide、nvcc Compiler Switches 与 CUDA Binary Utilities。

结论

本例的连续访存映射在固定输入上稳定快于跨步映射，说明线程到地址的对应关系是可直接测量的优化对象。这个结果只覆盖向量加法和本文设备、规模与编译配置；移到归约、GEMV 或融合算子时，需要重新建立相同口径的基线并检查其实际数据流。延伸案例可参考本站的归约求和与矩阵向量乘。
