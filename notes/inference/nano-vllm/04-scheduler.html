KV 块不足时的抢占

Scheduler.schedule() 在 decode 分支从 running 中选择请求。这些请求已经完成 prompt 处理，正在逐个生成新 token。生成时，模型要把新 token 的 Key 和 Value 写入 KV Cache。BlockManager.can_append(seq) 检查当前请求在下一步是否需要一个新的物理 KV 块，以及空闲块是否足够。它的条件是 len(seq) % block_size == 1：只有刚跨过块边界才需要新块；若当前块还有位置，即使空闲池为空，这一步也能继续。can_append() 源码

假设 running 依次是 A、B、C、D，A 正好需要新块，但空闲块为零。只等待 B、C、D 自然生成到结束，A 的下一步可能要等很久；当它们的输出很长，或系统持续有请求占用块时，A 会长时间没有响应。B、C、D 如果还能继续生成并最终结束，这个例子属于资源等待造成的请求饥饿或长尾延迟；如果多个请求都在块边界等新块，则可能出现无人能推进的资源停滞。代码因此把队尾 D 抢占，解除 D 对块的引用，再检查 A；还不够就继续从队尾撤回请求。它优先让队头请求取得资源，并没有保证每个请求都能立即前进。

抢占的代价从这四行可以看出：D 离开运行队列，块表与 num_cached_tokens 被清空，下次从等待队列重新走 prefill。BlockManager.deallocate() 解除 D 对块的引用；若某个块还被其他请求共享，它的引用计数不会降到零，因此这次抢占也未必马上腾出一个空闲块。deallocate() 源码 释放后的完整块若仍在哈希索引中，D 恢复时可能再次命中；如果块已被重新分配给不同内容，相应 token 就要重新计算。抢占用额外的状态切换与可能的重算，换取队头请求及时继续执行。

如果其他运行请求都已撤回，当前请求仍拿不到块，else 会连当前请求也抢占。这份实现随后要求 scheduled_seqs 非空；若本轮一个请求都没选中，assert scheduled_seqs 会报错。因此，这段逻辑解决的是常见的资源竞争，不能把它理解为对所有块容量配置都能完成请求的保证。

共享前缀与分块 prefill 的剩余计算量

remaining 是本轮还能计算的 token 数；num_tokens 是当前请求还需要计算的 token 数。两者分开，才能决定这轮是否放得下当前请求。block_table 保存这个请求按顺序使用的物理 KV 块编号。它为空时，说明还没有为当前执行阶段建立块映射：新请求会如此；被抢占后，deallocate() 清空块表，也会重新进入这条分支。

第一次分配时，can_allocate(seq) 按 token 内容和前缀哈希查找连续、完整、已经算过的 KV 块，并同时检查块容量。返回的 num_cached_blocks 是块数，乘上 block_size 才是可以跳过计算的 token 数。真正将这些共享块编号写进 seq.block_table 的是后面的 allocate(seq, num_cached_blocks)；它还会设置 seq.num_cached_tokens = num_cached_blocks * block_size。can_allocate() 与 allocate() 源码

例如，设每块容纳 16 个 token，请求 A 和 B 分词后的前 32 个 token 完全相同，后面的 token 不同，且两者各需 4 块。A 已算好前缀并使用 [5, 6, 7, 8]。B 第一次进入时可命中前两块，于是它的块表可以是 [5, 6, 11, 12]：5、6 保存两者共用的前缀 KV，11、12 留给 B 的不同部分。若 B 总长 64 个 token，num_cached_blocks = 2，这一分支得到 num_tokens = 64 - 2 × 16 = 32。这些编号是解释性示例，实际编号由空闲块池决定；复用要求 token ID 按块连续一致，文本看起来相似并不足够。

如果 B 的 32 个待计算 token 本轮只得到 20 个预算，seq.num_scheduled_tokens 就是 20。模型处理完后，postprocess() 把 20 加到 num_cached_tokens，此时它是 52。B 的 block_table 仍在；下一轮进入 else，计算 64 - 52 = 12。这里无需再减一次 32 个共享前缀 token，因为 num_cached_tokens 已经把复用的 32 和新算好的 20 都记入进度。抢占会清空块表和进度；恢复时重新走 if，再次查询仍可用的共享前缀。

if remaining < num_tokens and scheduled_seqs 规定：本轮已经选了其他请求，当前请求又放不进剩余预算，就先停下。只有本轮第一个被选中的请求可以使用不完整的 prefill chunk。这个条件使一次 prefill batch 不会同时放入多个仅处理了部分 prompt 的请求。

运行队列为何先取出再放回

popleft() 从队头取出准备调度的请求，体现这里优先考虑较早进入 running 的请求。pop() 同样是 deque 的高效两端操作；代码用它从队尾挑选被抢占者，保留队头的优先权。先把当前请求取出还有一个作用：资源不足时，self.running.pop() 取到的是其他运行请求，不会误把当前正在争取资源的请求当作第一个牺牲对象。

取出不代表运行请求已经完成。选中请求仍需留在 running，因为模型执行后 postprocess() 可能调用 self.running.remove(seq) 移除已结束的请求。scheduled_seqs 是本轮交给模型计算的列表；running 则保存跨轮次继续生成的请求。调度完成后，extendleft(reversed(scheduled_seqs)) 把选中的请求放回运行队头。

设 running = [A, B, C]，本轮最多选两个请求，三者都不需要抢占。popleft() 先后取出 A、B，队列暂时是 [C]，scheduled_seqs = [A, B]。extendleft() 会逐个从左侧插入，所以先把列表反转为 [B, A]，插入 B 再插入 A，最终恢复为 [A, B, C]。这也说明它不是把 A、B 轮换到队尾：本实现会让已选中的队头请求保持靠前，直到结束、被抢占，或受到其他调度条件限制。
