一个物理块的 `ref_count` 为 0、1、2 时，分别表示什么

要解决的问题是：A 和 B 共享同一个前缀块时，A 结束会不会把 B 正在使用的块释放？ ref_count 记录当前有多少个请求持有这个物理块。刚创建时是 0；A 使用时是 1；B 也复用它时是 2；若还有第三个请求共享，就是 3。此时 A 结束只会把引用数从 2 减到 1，B 仍可以读取这份 KV 数据。

allocate() 中，命中的块若已经被活动请求占用，就增加 ref_count；若命中的是空闲但内容尚未被覆盖的块，就从空闲队列移出，并把引用数设为 1。释放请求时，deallocate() 对它块表中的每个块减 1；只有减到 0 才放回空闲队列。allocate() 与 deallocate() 源码

图中的块 5 是解释性示例。ref_count = 0 表示当前没有请求持有，并不表示该块的旧内容立刻消失：_deallocate_block() 只把编号放回空闲队列，没有清空 hash 和 token_ids。旧内容尚未被新分配覆盖时，前缀缓存仍可能命中它；真正拿它写新内容时，_allocate_block() 才移除旧哈希映射并调用 reset()。

引擎、调度器和块管理器分别负责什么

这里要定位的是：这份文件管理的究竟是 GPU 上的 KV 数据，还是决定如何使用这些数据的记录？ BlockManager 保存的是 CPU 侧的块元数据：每个编号对应的 Block、空闲与使用中的编号，以及从前缀哈希查块编号的字典。Block 的 token_ids 用来核对缓存内容；实际的 Key/Value 张量由模型执行器持有。ModelRunner 源码

请求由 LLMEngine.add_request() 加入调度器，generate() 驱动后续轮次。Scheduler.schedule() 决定本轮选哪些请求，并调用 BlockManager 检查、分配或追加块；请求被抢占时由 Scheduler.preempt() 解除块引用，正常结束时由 Scheduler.postprocess() 解除引用。LLMEngine 同时持有 ModelRunner，后者按请求的块表把本轮 token 的 KV 写入 GPU 张量。图中的两条分支说明了职责边界：块管理器维护编号和占用关系，执行器计算并保存实际 K/V 数值。LLMEngine、Scheduler

`_allocate_block` 的下划线与 `__init__` 的双下划线有何区别

问题落在方法名上：_allocate_block() 前面只有一个下划线，Python 会禁止外部调用吗？ 不会。单个前导下划线是“供类内部使用”的命名约定。这个方法只从空闲队列取出一个物理块、核对引用数并准备覆盖旧内容；对外的 allocate(seq, num_cached_blocks) 会先处理前缀共享，再在未命中的位置调用 _allocate_block()。调用方应使用完成整套步骤的公开方法，而不是绕过它直接分配一个块。

笔记里还比较了另外两种名字，含义不同：

写法 在此处的例子 Python 如何处理
_name _allocate_block 约定为内部接口，名称本身仍可访问。
__name 假设写成 __secret 类内名称会改写为 _BlockManager__secret；本文件没有这种成员。
__name__ __init__ Python 识别的特殊方法；构造对象时自动调用。

查询前缀缓存时，为什么要把上一块的哈希接进来

要匹配的是从请求开头到当前块为止的完整前缀，而不只是当前块本身。 设逻辑块 0、1 的 token 分别是 T₀、T₁。首块得到 h₀ = H(T₀)；下一块把 h₀ 的 8 字节表示与 T₁ 的字节依次送进哈希计算器，得到 h₁ = H(h₀ ∥ T₁)。分别计算两个块的哈希再相加，不能表示这样一段有顺序的前缀。相同的 T₁ 接在不同的首块后面通常得到不同的前缀哈希；若发生哈希碰撞，后文的 token 核对会阻止错误复用。代码每次创建一个哈希计算器，通过传入上一个结果形成这条链。compute_hash() 与 can_allocate() 源码

图中的 A、B 前两块 token 相同，因此查询 B 时先命中块 0，再以相同的 h₀ 计算并命中块 1。hash_blocks() 在模型算完完整块后，把链式哈希登记到 hash_to_block_id；can_allocate() 从请求开头逐块查这个字典，遇到首个不匹配就停止。循环只检查 range(seq.num_blocks - 1)，即当前最后一个逻辑块不作为可复用前缀候选。

哈希已经命中，为什么还要比较 `token_ids`

疑问是：字典已经找到了块编号，为什么还可能判定失败？ 哈希把大量不同的 token 序列压缩为有限大小的整数，理论上不同内容可能得到同一个值。查到的 block_id 只是候选；代码再比较该物理块保存的当前块 token_ids 与请求的当前块是否逐项相同。若不同，就不复用，并停止检查后面的块。前面的完整块已经在前几次循环中逐一核对，所以这里只需要检查当前块。

例如，设块大小为 2，假设块 0 的哈希恰好把内容 [1, 2] 与 [9, 9] 映射成相同的整数。查询请求 [9, 9] 时字典可能返回存着 [1, 2] 的块；第二个条件会挡住这次错误复用。这个数字例子只说明判断顺序，不表示真实运行中观测到哈希碰撞。

`can_append()` 为什么只在余数为 1 时要求空闲块

问题在于：块大小为 4 时，序列长度恰好为 4 看起来已经填满，为什么此时不检查新块；长度变成 5 才检查？ Sequence 的 token 列表包含刚采样出来、尚未为其计算 KV 的最后一个 token。decode 本轮要处理这个最后的 token。长度为 4 时，它仍占第一个逻辑块的末尾位置；本轮处理后又采样出第 5 个 token，序列长度变为 5。下一轮处理第 5 个 token 时，它才需要第二个物理块。Sequence.append_token()

括号里的比较式产生布尔值：余数是 1 时为 True，在整数比较中相当于 1，所以 can_append() 要求空闲块数至少为 1；其他余数得到 False，相当于 0，条件总能通过。真正取出新块的是紧接着的 may_append()。图中长度 4、5、6 与代码的余数 0、1、2 一一对应。
